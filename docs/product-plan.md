# CodeGuard 首版产品与技术方案

更新日期：2026-10-18。状态：第一阶段 Git 工作台及第二阶段首批（模型配置、本次提交评审）已实现并验证；第二阶段其余评审范围与第三阶段尚未实现。启动见根目录 README.md，任务见 `.scratch/git-workbench/` 与 `.scratch/ai-review/`。

## 1. 产品定位

CodeGuard 是面向个人开发者的 Windows 桌面 Git 工具。它帮助使用者看懂 AI 生成的改动、核对问题和证据，并完成日常提交、推送、拉取与本地分支合并。

界面风格和操作主要参考 GitKraken，改动选择参考 VS Code Git。AI 直接接入用户配置的模型服务。工具解释和评审代码；编码助手负责修复；使用者决定执行 Git 操作。

核心流程：选择改动 → 理解变化 → 查看问题与验证证据 → 必要时交给编码助手 → 选定提交内容 → 预览并执行操作。

### 已确认与方案建议

已确认：个人自用、Windows 桌面、默认全部本地改动、摘要优先、独立模型接入、可配置规范、需求可选、评审只提醒、手动检查、默认仅快进拉取、冲突外部处理，以及 TS/JS、Python、Rust、Go、C++ 的评审需求。

第一阶段已采用 Electron、React 和 TypeScript，记录于 ADR-0001。模型配置、分析器顺序和后续阶段中的实现细节仍按下文建议，在相应阶段验证。

## 2. 首版范围

| 能力 | 首版行为 |
| --- | --- |
| 仓库 | 添加已有本地仓库、切换、从列表移除；移除不删除目录 |
| 改动 | 显示已暂存、未暂存、未跟踪文件；查看差异；整文件暂存与取消暂存 |
| 历史 | 提交列表与彩色分支图；选择提交查看说明、文件、差异和评审 |
| 分支 | 查看、切换本地分支；选择源分支，预览并合并到当前分支 |
| AI 评审 | 当前全部本地改动、本次提交、单个历史提交、分支差异 |
| 评审依据 | 用户配置的规范、项目规范、可选需求文档 |
| 提交 | 从最终暂存区生成说明、人工编辑、提交、显示真实结果 |
| 同步 | 获取远端状态、仅快进拉取、普通推送；显示方向和领先/落后情况 |
| 验证 | 手动运行已配置的检查，记录命令、对象、结果和时间 |
| 修复交接 | 复制问题、位置、触发条件、证据和建议给编码助手 |
| 设置 | 模型服务、规范、文件排除、验证命令；按仓库保存选择 |

首版边界：不直接修改源码，不生成或应用修复补丁，不内置冲突编辑器；不包含远程 PR 工作流、强制推送、硬重置、自动变基、自动暂存保护、自动解决冲突或插件市场。克隆、分支创建、按块/按行暂存作为后续候选，不扩大本次确认范围。

## 3. 界面与信息层级

建议使用克制的深色工作台、彩色分支线、紧凑列表和可调整面板。颜色表达分支、增删和状态，文字及图标同时表达含义。保持原创界面，不使用 GitKraken 的商标、图标或素材。

```text
仓库 / 当前分支                         获取  拉取  推送  设置
────────────────────────────────────────────────────────────
仓库与分支 │ 当前改动 | 提交历史             │ 评审侧栏
           │                                │
本地分支   │ 默认：行为变化、文件与提交选择   │ 范围 / 依据
远端分支   │ 历史：彩色提交图与提交列表       │ 问题与证据
           │ 点文件：源码差异                │ 验证结果
────────────────────────────────────────────────────────────
当前范围 / 数据状态 / 操作结果                   上下文主操作
```

默认打开上次仓库的“当前改动”。不先展示统计仪表盘。设置放侧抽屉，不在主界面堆放模型参数、规则选项或分析器开关。

### 当前改动

主区先呈现“之前怎样 → 现在怎样 → 影响哪些入口”，下面列出文件；侧栏显示待处理问题与验证状态。文件按未暂存、已暂存、未跟踪分组。查看全部改动不会自动暂存文件。

点击文件打开差异，保留“返回概览”。暂存、取消暂存直接响应点击，不逐次弹确认框。提交说明抽屉展示暂存文件和最终说明，“提交 N 个文件”按钮就是本次提交确认。

### 提交历史

主区展示彩色提交图、摘要、分支标签、作者和时间。选择普通提交查看该次变化；选择分支比较入口查看源分支引入的改动。当前分支始终可辨认，选中历史提交不会切换工作区。

从分支菜单选择“合并到当前分支”，先展示源 → 目标、涉及提交和文件，再由人执行。首版不使用拖拽直接触发分支写操作。

### 问题卡片

默认展开最需要处理的问题，卡片显示优先级、具体触发条件、后果、代码位置和证据状态。点击位置查看差异，展开后查看关联代码及规则来源。提供“待处理／已处理／忽略”和“复制给编码助手”。

“已处理”是人工处置记录，不能自动改称“已验证修复”。后续复查应单独显示是否仍能发现该问题。

### 操作反馈

预览展示在当前抽屉或面板，不串联多个确认弹窗。提交、推送、合并分别执行。成功、失败、冲突和状态已变化各有明确文字；失败时保留提交草稿和用户选择。

## 4. 评审范围与版本

界面始终显示范围名称、目标及版本状态，详细 Git 标识放在可展开区域。

| 范围 | 分析对象 | 注意事项 |
| --- | --- | --- |
| 全部本地改动 | HEAD 到当前工作区，并额外纳入经排除规则过滤的未跟踪文件 | 默认查看入口，不等于本次提交 |
| 本次提交 | HEAD 到索引中的内容 | 同一文件未暂存的新修改不能替代索引版本 |
| 单个历史提交 | 普通提交的父版本到该提交 | 根提交按空树比较；合并提交默认第一父视角并明确标注，可切换父视角 |
| 分支差异 | 源与目标的共同祖先到源分支 | 显示源分支引入的变化，不冒充合并后的最终结果 |

这些比较语义遵循 [Git diff 文档](https://git-scm.com/docs/git-diff)。无共同祖先、浅历史缺失或无法解析引用时显示具体原因，不悄悄更换比较范围。

一次评审固定快照，关联仓库、HEAD、索引、文件内容、需求文档、有效规范及模型配置版本。内容或评审依据变化后，旧结论显示“基于旧版本”；失败或被跳过的部分不能显示为已评审。

全部改动评审完成后，如果本次暂存区只包含其中一部分，显示两者差别；不能直接标记“本次提交已评审”。可复用有效证据，但提交范围的结论需要重新核对。提交说明始终从最终暂存区生成。

## 5. AI 评审流程

用户点击“评审”后，在一个后台任务中完成以下步骤，界面可继续浏览差异：

1. 固定范围和版本，收集差异、相关实现、必要测试与选定依据。
2. 显示分析覆盖范围；超出配置预算时分批或由用户缩小范围，避免默认发送整个仓库。
3. 生成行为变化摘要；按内容选择需要的检查视角。
4. 分别检查代码正确性、规范符合度和需求符合度。工具已有确定性结果时不重复制造风格建议。
5. 对候选问题再核验触发条件、代码证据、行号和是否由本次改动引入，合并重复问题。
6. 展示问题、覆盖情况、验证结果及未知项；保留可追溯版本。

首版可用多个有明确职责的模型步骤实现，不预设复杂自治代理团队。一个“评审”按钮即可，不向用户暴露一排技能或代理角色。

AI 可以提出进一步评审的建议、生成提交草稿和准备结构化操作建议，程序再生成可检查的操作预览；实际写操作等待使用者确认。首版从桌面界面进入，外部编码助手通过 CLI 或 MCP 发起请求作为后续候选接口，不把该集成默认为已实现。

### 发现格式

每条问题记录：优先级、问题描述、触发条件、相关位置、证据、后果、修复方向、所属评审维度及依据来源。跨语言接口问题可关联多处代码。

证据状态分为“检查结果支持／静态分析支持／AI 推断待确认”，不把模型自报分数当成可靠概率。规范问题标为约定符合性；启发式设计建议与确定缺陷区分呈现。

输出“本范围未发现问题”，不输出“代码完全安全”。没有需求文档时显示“未核对需求”，检查未执行时显示“未运行”。

### 评审与 Git 的关系

评审只提醒，不强制拦截。未评审、结论过期、有待处理问题时，使用者仍可在看到提醒后提交或合并。正常路径不要求填写豁免理由。

仓库处于冲突、存在锁或操作会覆盖改动等实际 Git 条件仍需处理。这些属于执行条件，不是 AI 评审门禁。

## 6. 需求与可配置代码规范

需求文档按次可选，首版建议支持 Markdown、纯文本和用户直接输入的需求说明。复杂文档导入后续增加。需求与代码规范各自有来源、版本和评审状态。

规范设置提供三个层次：通用评审基线、自动发现的项目规范、用户明确配置的覆盖。优先级建议为“用户明确覆盖 > 项目约定 > 通用基线”；不同来源冲突时展示生效规则及来源。

用户可以在设置中编辑规范，也可主动将共享规则保存到仓库。建议使用 `.codeguard/review.md`，无需另学规则语言。例如用户可以要求“错误必须包含上下文”“公共接口变化需要兼容性说明”“不要重复报告格式化工具能处理的问题”。

自动发现候选包括 CONTRIBUTING、CODING_STANDARDS、用户指定文档及语言工具配置。读取文件中的约定不等于执行其中脚本；不把仓库文本当成授权外传数据、运行命令或改变工具行为的指令。

语言规则可分组配置：TS/JS 关注类型与异步行为，Python 关注异常与资源边界，Rust 关注错误传播与 unsafe，Go 关注错误处理与并发，C++ 关注生命周期与资源管理。这些是候选检查方向，不代表工具已经能够完整证明相关性质。

变更规范后保留历史评审所用版本，当前结论注明依据已更新。

## 7. 多语言支持与图示

首版覆盖 TypeScript、JavaScript、Python、Rust、Go、C++ 的差异、AI 文本评审、需求和规范核对、配置检查及修复交接。不承诺所有语言具有同等精度的符号解析或跨项目语义能力。

| 层次 | 首版建议 |
| --- | --- |
| 差异与代码证据 | 所列语言均支持，包含常见扩展名和路径 |
| AI 上下文 | 按改动与相关代码收集；按预算限制；显示覆盖情况 |
| 外部检查 | 通过用户配置的命令接入已有工具，不自动安装或修改项目 |
| 行为示意 | 按需生成小型流程图或前后对比，明确标为解释性示意 |
| 静态关系 | 首版先保留可追溯的文件依赖；符号与调用解析按技术实验结果逐步开放 |

检查配置示例：TS/JS 的测试、类型检查和 lint；Python 的测试与 lint；Rust 的测试和 clippy；Go 的测试与 vet；C++ 的项目构建、测试或静态检查。实际命令由用户选择，不假定工具已安装或命令适用于所有仓库。

show-me 的价值落实为“用最小图解释当前变化”。可优先采用前后对比、局部流程和引用位置。解析器确认、AI 推断和未知关系使用不同标识；模型生成的行为图不命名为真实调用图。全仓库调用图留待后续。

## 8. 检查命令与验证证据

每个仓库可以配置命令、参数和工作目录，主界面通过一个“运行检查”入口选择执行。首次保存配置时展示具体内容，执行由用户点击触发；不因打开仓库或启动评审自动运行项目脚本。

结果至少包括：命令、执行目录、开始/结束时间、退出状态、日志与实际代码对象。状态区分未运行、运行中、通过、失败、取消和结果已过期。

首版默认在当前工作区运行检查。因此：

- 未暂存改动存在时，检查对象可能不同于索引中的本次提交，必须显示差异。
- 查看历史提交或其他分支时，当前工作区检查不能算作被选中对象的验证。
- 检查期间代码变化，结果注明对象发生变化；格式化或测试产生改动时刷新文件状态。
- 在独立快照环境验证暂存区或历史版本作为后续增强，不自动切换或清理真实仓库。

AI 可以解释真实输出，不能编造测试通过、执行次数、性能提升或验证覆盖。

## 9. Git 操作流程

### 提交

选文件暂存 → 展示本次提交 → 生成并编辑说明 → 显示评审与检查状态 → 点击提交 → 显示哈希与实际结果。

说明采用简短标题和必要正文，支持用户模板，默认不强制 Conventional Commits。不得包含未暂存内容或虚构测试、问题编号和兼容性承诺。索引变化后保留草稿并提示更新。

提交前重核索引和目标，提交后核验实际提交树。仓库钩子或外部工具可能在执行期间修改索引，所以不能承诺“执行前核对即可原子保证内容相同”。遵循真实钩子、签名和提交结果，不跳过钩子、不自动回滚。若实际提交与评审快照不同，展示事实并标记旧评审；后续动作需新的操作预览，仍不强制重新评审。[Git commit](https://git-scm.com/docs/git-commit)、[Git hooks](https://git-scm.com/docs/githooks)。

### 推送

显示本地分支 → 远端/分支及待推送提交，用户确认后执行普通推送。没有上游时先选择目标，不猜测远端。非快进拒绝、认证和网络错误分别提示；首版不提供强制推送。

### 拉取

获取远端状态 → 能快进则更新 → 本地与远端分叉时展示比较及“显式合并”入口。使用明确的仅快进策略，不依赖用户全局 Git 默认设置；fetch 更新远端跟踪状态，不等于工作区已更新。[Git pull](https://git-scm.com/docs/git-pull)。

### 切换分支

展示目标分支，检查本地改动状态。若存在覆盖风险则保留当前状态并说明原因，不自动 stash、不强制切换。分支选择与历史浏览是两个动作。

### 合并与冲突

选择源分支 → 展示源 → 当前目标、提交范围、文件及已有评审 → 用户确认合并 → 显示真实结果。

存在目标分支独有改动时，提醒源分支评审不等于已验证最终集成结果；合并预检仅作参考，不能承诺无冲突或无语义问题。

遇到冲突后列出冲突文件，保留 Git 当前进行中状态；支持打开外部编辑器和复制处理说明。编码助手处理后，刷新并由用户确认暂存与完成合并。提供用户显式发起的“中止本次合并”，预览适用状态和 Git 的实际限制；不中断外部正在进行的操作，不自动清理残留文件。

所有 Git 写操作按仓库排队；外部编辑器和 Git 客户端仍可能同时修改仓库，因此执行前后都需刷新。锁、冲突、rebase 等状态按真实原因显示，不删除锁文件冒充修复。

## 10. 模型、数据与配置

设置页提供服务地址、模型名称、密钥与连接测试。首版建议选定一种兼容接口协议并验证一个服务端；“可自行配置服务”不等于任意供应商都无需适配。首个适配协议在技术实验中确定。

调用由用户触发，显示分析范围和必要上下文预览。排除配置涵盖密钥文件、生成物、二进制、超大文件及用户指定路径；排除项也适用于摘要、日志和修复交接，不能从其他上下文路径绕过。外部引用、符号链接与子模块不自动扩大到未授权目录。

密钥使用系统保护的本地存储，不进入仓库配置、普通日志或界面导出。模型响应与仓库文本作为不可信内容处理，不允许其直接发起 Git 写操作或任意命令。

用户级设置保存模型与个人默认项；仓库本地设置保存选择、排除和命令。共享规则需要用户主动保存到仓库，添加仓库本身不写入项目文件。

费用已知时展示真实用量；服务不返回价格或用量时显示未知。上下文预算可配置，大范围分析先提示缩小或分批。取消会停止后续请求，已产生调用不伪装为免费或已撤销。

无网络时仍可查看差异、暂存、编辑提交草稿和执行可用的本地 Git 操作。模型失败保留现有结果并标注失败部分。

## 11. 实现结构建议

第一阶段采用 Electron + React + TypeScript：界面主要使用统一的前端技术，本地服务借助主进程调用系统 Git。优点是实现工作台和进程交互方便，代价是安装体积和运行开销。取舍见 `docs/adr/0001-local-electron-workbench.md`；安装包体积仍需在后续打包阶段评估。

界面进程只表达用户意图；本地服务负责 Git、快照、模型请求、检查执行和系统保护的密钥存储。通过有参数校验的业务接口通信，不向页面暴露任意命令执行入口。Electron 实现应启用上下文隔离及渲染沙箱，关闭渲染端 Node 集成。上下文隔离与操作系统进程沙箱是不同机制。[进程模型](https://www.electronjs.org/docs/latest/tutorial/process-model)、[上下文隔离](https://www.electronjs.org/docs/latest/tutorial/context-isolation)、[沙箱](https://www.electronjs.org/docs/latest/tutorial/sandbox)。

Windows 可使用 Electron safeStorage 的系统加密能力保存密钥；它不承诺抵御同一登录用户下所有程序。[safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage)。

| 模块 | 责任 |
| --- | --- |
| 仓库服务 | 状态、差异、历史、分支、串行写操作、错误与刷新 |
| 快照服务 | 固定范围、索引/内容标识、过期检测、证据关联 |
| 评审服务 | 上下文选择、有效规则、模型步骤、候选复核与缓存 |
| 检查服务 | 用户配置、执行、取消、日志与对象匹配 |
| 设置服务 | 模型、密钥、规则、排除和仓库偏好 |
| 界面 | 概览、图与列表、差异、问题卡片、操作预览 |

Git 调用使用可执行文件和参数数组，明确仓库路径，不拼接不可信 shell 文本。检查命令属于用户显式配置的执行入口，单独处理其 shell 与参数规则，不与 Git 参数封装混为一谈。

核心数据为仓库、评审范围、快照、评审运行、发现、检查运行、提交草稿和操作记录。发现、检查证据和草稿均保留适用版本。首版采用本地持久化，暂不增加云同步、账号或服务端。

## 12. 交付阶段与验收

### 阶段一：Git 工作台骨架

交付仓库、改动、整文件暂存、差异、提交历史图、提交与分支状态。通过临时仓库覆盖暂存后再次编辑、空仓库、重命名、删除、未跟踪文件以及 Windows 特殊路径。

通过条件：界面范围与真实 Git 状态一致；不会把未暂存修改算进本次提交；提交失败不丢草稿。

### 阶段二：AI 评审与配置

2026-10-18 首批已实现：兼容 Chat Completions 的模型配置与连接测试、系统保护密钥、固定暂存快照与发送预览、可选文本规范和需求、摘要与问题证据、位置校验、取消、复制交接及过期状态。评审不拦截提交。已使用本机模拟服务验证真实 HTTP 与桌面桥接；尚未使用真实供应商评价评审质量。项目规范自动发现、其他评审范围、相关代码上下文与跨语言质量评估留待下一批。

交付自行配置模型、规范与需求选择、摘要、问题证据、三类评审对象、修复交接和过期状态。所列语言均进入差异与文本评审验收，分别用真实样例评估质量。

通过条件：每条问题可定位；无需求显示未核对；无检查显示未运行；超时、无效行号、部分覆盖和文件变化不会显示成完整通过。

### 阶段三：同步、合并与验证

交付手动检查、推送、仅快进拉取、分叉预览、显式合并及外部冲突处理后的继续/中止流程。

通过条件：检查对象标注准确；分叉不会悄悄变基；冲突可理解并保留工作；钩子和签名错误如实反馈；操作对象变化会更新预览，评审问题仍不构成强制门禁。

### 实际使用验收

由用户用真实任务比较原有流程与新工具：看懂一次改动需要多久、多少问题确有价值、是否还需频繁切换终端、完成提交与合并是否更清楚。记录误报、遗漏、成本和耗时，不用建议数量或综合质量分数衡量价值。

技术实验另外验证：大历史图的响应、超大 diff、模型结构化输出、跨语言上下文、Windows 检查取消、现有 Git 认证，以及钩子修改索引后的结果核验。验证写操作使用临时仓库。

## 13. 当前建议与下一步

第一阶段已交付两种主视图、文件级暂存、真实差异、提交预览、提交与历史图。第二阶段首批已在右栏接入本次提交的 AI 评审，模型配置收纳于独立面板；当前尚不生成提交说明，也不自动修复源码。

后续接入其他评审范围、项目规范发现和必要上下文，使用真实任务评估模型质量，再推进同步、合并与检查。首批模型协议、密钥与评审快照取舍见 ADR-0002。
